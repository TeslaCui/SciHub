# 实验方案更新与后续步骤采用 · v1.0.7

本方案按用户确认的语义设计：保护进行中实验已经完成、当前正在操作及已有记录的步骤；方案更新不自动影响运行快照；操作者另行审核后才采用新版未开始步骤。已结束实验完整保留原快照，不要求所有历史实验与新方案一致。

## 两道审核门

1. 编辑或上传方案新版本，点击“审核并保存修改”。界面列出各进行中实验的保护范围、逐步差异及拒绝原因。保护范围是从第一步到 `max(current_step, 最后一条已开始、完成或已有记录的步骤)` 的完整前缀，防止在已执行工序前插入、移除或重排步骤。开始/完成时间、数值零、附件、备注、勾选，以及任何已保存值对象均纳入保护。
2. 受保护定义须逐项一致：标题、说明、顺序、字段名称/单位/类型及其他字段属性、注意事项、时长、热解程序和旧完成条目。科学单位区分大小写；不按相似名称、AI 同义或删空白后的猜测判定。实测值可以不同，不拿数值判断模板一致。
3. 通过后由操作者点击“确认更新方案”。数据库锁定方案、其运行实验及步骤，重新审核并核对审核时的版本。审核后有新增记录、完成进度或方案变化时整笔拒绝。方案保存仅改变模板，任何运行或结束实验的 ID、定义、实测值、备注、附件引用、时间和关系均不写入。
4. 进行中实验显示“与方案不一致”，可以继续使用原快照，也可以选择“审核采用新版后续步骤”。数据库单独核对本次实验的受保护前缀，拒绝不匹配、已结束、已合并和旧关联实验。当前步骤保持不变，只替换保护范围之后的未开始定义。
5. 替换不搬移实测值。保留受保护行全部列和未来已存在行的 ID；新增未来步骤生成新 ID。若新版缩短尾步，审核逐项列出待移除的未开始步骤，必须勾选明确批准；没有确认时不执行移除。采用前后的完整快照写入私密审计，失败事务回滚。

## 数据模型、权限和历史

新增 `experiment_plan_update_audits`，只允许账号读取自己的审计。记录方案或实验 ID、操作类型、完整前后快照、审核快照、操作者和时间；客户端不能直接改写或删除。ID 用作不可变来源标识，不依赖活跃方案/实验的外键级联删除，删除活跃对象后仍保留审计来源。账号级的管理员删除依然受 Auth 的账号生命周期管理。

新接口：`research_review_plan_update`、`research_commit_plan_update`、`research_adopt_plan_update`、`research_start_run`。`research_save_plan` 保留既有签名并增加同样的服务端审核；更新方案按位置保留已有模板步骤 ID，不再整套先删后建。起跑在一个事务中取得同一版模板并生成完整实验快照。

所有写接口核对 `auth.uid()` 和对象所有权。审核读接口遵循 RLS，私密审计启用 RLS，服务端写接口在明确所有权条件下操作。收紧客户端对模板及执行定义的直接写入权限，继续允许既有客户端保存执行值、备注、媒体、状态、时间和旧关联；方案/实验重命名继续可用，归属及来源关系不能直接改写。

上传新版本按新文档生成候选，不用旧标题、旧单位或 AI 同义匹配掩盖真实改动。重新解析只生成草稿，不自动保存或迁移。移除首页自动补时长写回，首页继续显示已保存时长及现有规则计算出的提示。

详情“查看更新审核记录”显示最近 20 条摘要；完整快照保留在私密表中。旧更新日志与执行快照原样保留，不伪造旧审核，也不把历史日志描述为完整旧版本备份。尚未提供审计一键恢复或长期历史分页入口。

## 旧数据与上线顺序

此次仅新增结构/接口及调整权限，不扫描转换、清空或改写历史数据和附件。无法核对的旧方案、非连续已执行步骤或归属异常保持原样并阻止更新。旧字段缺少 `unit`/`type` 时仅在比较中按空串处理，不把科研值转换或补写。

旧完成条目在方案中保存为 `checklist`，在执行快照中保存为 `checks` 的键。审核按原始名称集合核对，不比较勾选值；旧执行对象没有保存条目顺序，不能据此推断工序顺序。编辑器保留并显示这些旧条目，保留字段额外属性，不自动转成新的记录字段。采用前还核对旧模板步骤位置连续，避免旧缺口让候选数组位置与实际步骤错配。

旧缓存客户端仍能查看和记录既有实验，但其直接改执行定义、旧重新解析和旧起跑路径会被权限拒绝。必须更新到 v1.0.7 后使用新审核及原子起跑；旧客户端起跑产生的未完成准备记录不得自动清理。网站比数据库先部署时，新操作收到接口不可用错误，保留草稿或原快照，不回退到多次写入。

数据库变更提案：`docs/proposals/reviewed-plan-updates.sql`。尚未获得本次部署授权时不得生成生产迁移或推送发布。批准后新增迁移，同步参考 schema，核实官方 Supabase 集成和 Pages 部署结果；回退前端不能视为回退数据库权限。

## 验证范围

先在独立 PGlite 数据库应用旧迁移并建立虚构旧方案/执行数据，再应用新提案两次，核对所有旧行、ID、零值、关系和附件引用保持一致。测试覆盖保护前缀冲突、当前步骤单位变化、后续允许更新、审核后写入、采用事务回滚、重复/跨账号调用、直接 API 权限及账号私密审计。线上写入仅使用专用内测账号和 `[内测]` 虚构数据，未授权删除的测试记录保留。
